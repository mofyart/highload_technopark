## Глава 1. Тема и целевая аудитория

### 1.1 Тема проекта, рыночная ниша и аналоги

**Выбранная тема:** проектирование бэкенда высоконагруженного B2C-облачного хранилища данных на примере сервиса **«Облако Mail»**.

**Реальные аналоги:** Google Drive, Apple iCloud, Dropbox, Microsoft OneDrive, Яндекс Диск. Наличие пяти независимых глобальных и локальных игроков на протяжении последних 10–15 лет однозначно подтверждает существование устойчивой и крупной рыночной ниши — потребности массового пользователя в резервном копировании фото/видео с мобильных устройств, синхронизации файлов между устройствами и обмене контентом по ссылке.

### 1.2 Целевая аудитория: размер и локализация

### 1.3 Функционал MVP

Для проектирования выделены следующие **5 ключевых функций**, покрывающих полный жизненный цикл файла — от поступления с устройства клиента до совместного доступа через публичный интернет:

1. **Многопоточная загрузка файлов.** Клиент разбивает файл на блоки и загружает их параллельно;
2. **Регистрация и авторизация** Система авторизации пользователя и регистрация новых;
3. **Эмуляция виртуальной файловой системы.** Создание, переименование, перемещение и удаление папок;
4. **Публичный доступ по ссылке и контроль прав.** Генерация токенов доступа с ограничением срока действия и уровня прав (просмотр / редактирование / скачивание);
5. **Управление дисковой квотой (Оверквота).** Кросс-сервисный микросервис учёта занятого пространства Облака;
6. **Скачивание файлов.** Пользователь скачивает файлы из Облака;

## Глава 3. Глобальная балансировка нагрузки (GSLB)

Глобальная балансировка (**GSLB — Global Scale Load Balancing**) отвечает на вопрос «в какой из нескольких географически разнесённых ДЦ направить запрос пользователя».

### 3.1 Функциональное разбиение по доменам

Функции MVP (§1.3) и типы запросов (§2.2.3) группируются в **5 доменов** по требованиям к консистентности и длительности сессии — это определяет, какие домены можно балансировать между ДЦ свободно, а какие требуют привязки к одному ДЦ:

| Домен | Функции MVP (§1.3) | Характер трафика | Требование к консистентности |
|---|---|---|---|
| Auth | Авторизация, refresh-токен | Короткие запросы, read-heavy | **Stateless для проверки, строгая для security-записей** — проверка JWT самодостаточна; но отзыв refresh-токена, смена пароля и бан должны мгновенно разойтись по всем ДЦ через primary|
| Metadata/FS | Листинг, CRUD папок | Короткие запросы, читаются часто | **Eventual** — листинг допускает краткое отставание реплики; редкие CRUD-записи идут к одному писателю на пользователя, поэтому конфликтов нет |
| Quota | Проверка/обновление квоты | Короткие запросы, control-plane | **Строгая** — счётчик занятого места: независимый инкремент в двух ДЦ разъедет значение и позволит превысить квоту |
| Object Storage | Многопоточная загрузка, скачивание | Длинные multipart-сессии, основной объём трафика | **Eventual** — blob после записи неизменяем, реплики сходятся без конфликта; multipart-сессию фиксируем за одним ДЦ, иначе переключение рвёт TCP |
| Public/Edge | Публичный доступ по ссылке, превью | Короткие кэшируемые GET, читаются анонимно | **Нет** — превью и публичные ссылки читаются анонимно, краткое отставание кэша некритично |

### 3.2 Обоснование расположения ДЦ (влияние на продуктовые метрики)

Расположение ДЦ определяется географией аудитории: Россия ≈ 74%, Турция ≈ 9%, Казахстан ≈ 4,5%, остальной мир ≈ 12,5%.

| Регион | Доля аудитории | ДЦ | Обоснование |
|---|---|---|---|
| **Primary — Россия (Москва)** | ≈ 74% | 4 зоны доступности Tier III (MS1, GZ1, ME1, PA2) | Основная масса DAU; требование 152-ФЗ о локализации персональных данных граждан РФ |
| **Secondary — Казахстан (Косшы / Астана)** | ≈ 4,5% | 2 зоны доступности Tier III (QazCloud + KazTeleport) | Локальное законодательство Казахстана (Постановление Правительства РК №832 о резервировании); снижает RTT для Центральной Азии |
| **Без выделенного ДЦ — Турция + остальной мир** | ≈ 21,5% | — обслуживаются из primary | Аудитория фрагментирована по множеству стран, ни один сегмент не достигает порога, оправдывающего собственный ДЦ; обслуживается через международный транзит primary-региона (upstream AS47764 включает Telia AS1299); кэшируемая часть трафика (превью, публичные ссылки) выносится на edge/CDN-узлы ближе к пользователю |

### 3.3 Распределение запросов по ДЦ

Доли аудитории (§3.2) применены к итоговым RPS (§2.2.3) и трафику (§2.2.2):

| ДЦ | Доля | RPS (сред. / пик) | Трафик (пик, Гбит/с / сутки, ГБ) |
|---|---|---|---|
| Россия (primary) | 74% | 895 / 3574 | 39,7 / 107 200 |
| Казахстан (secondary) | 4,5% | 54 / 217 | 2,4 / 6 520 |
| Турция + остальной мир (обслуживаются из primary) | 21,5% | 260 / 1038 | 11,5 / 31 150 |
| **Итого** | 100% | 1210 / 4830 | 53,7 / 144 875 |

> **Примечание.** Формула: `RPS_регион = RPS_всего × доля_аудитории`, аналогично для трафика. 

### 3.4 Схема DNS-балансировки

Двухуровневая схема:

1. **Между регионами (GSLB) — Latency-based DNS**: резолвер получает адрес ДЦ с минимальным RTT из региона запроса. Выбран вместо Geo-based DNS (по IP-геолокации), т.к. latency-based устойчивее к неточной геолокации резолвера провайдера и лучше отражает реальную сетевую доступность. Веса ответа пропорциональны распределению из §3.3 (74% / 4,5% / 21,5% → RU).
2. **Внутри региона (между 4 зонами доступности Москвы) — Weighted Round-Robin DNS** с весами, равными доле ёмкости каждой зоны — задержка между зонами одного региона мала, поэтому нет смысла терять время на DNS TTL ради выбора конкретной зоны.

> **Примечание.** Короткий TTL (десятки секунд) на GSLB-записях — чтобы быстро вывести из ответа упавший регион (недостаток классического Round-Robin DNS — «долгое отключение упавшего сервера», слайд презентации). Resolver видит IP DNS-резолвера, а не клиента — для повышения точности latency-оценки предусмотрена поддержка EDNS Client Subnet (передача подсети клиента в DNS-запросе).

### 3.5 Схема Anycast-балансировки

Anycast применяется **выборочно**, только там, где обрыв TCP-сессии при смене маршрута не критичен:

| Слой | Anycast? | Обоснование |
|---|---|---|
| DNS-серверы | Да | Классический сценарий — короткие UDP-запросы, недорогое переключение |
| Public/Edge (превью, публичные ссылки) | Да | Короткие кэшируемые GET-запросы (§3.1) — переподключение к другому PoP не заметно пользователю |
| Object Storage data-plane (загрузка/скачивание) | **Нет** | Multipart-сессия длится всё время передачи (§2.2.3, N=1,6 блока/файл, крупные видео — десятки блоков); смена ДЦ на BGP-маршруте разрывает TCP-соединение (недостаток BGP Anycast — «поломка соединений при перескоке трафика между ДЦ», слайд презентации). Вместо anycast — sticky-маршрутизация через latency-based DNS (§3.4), фиксирующая ДЦ на весь сеанс |
| Auth / Quota / Metadata | Нет | Требуют строгой консистентности к одному источнику истины (primary-регион, §3.1) — anycast не решает эту задачу, нужен GSLB c весами |

> **Примечание.** Anycast для собственной AS (по образцу AS47764) требует отдельной сети /24 и BGP-анонса из каждой точки присутствия. Для сервиса с 2 регионами это оправдано только для узкого edge-слоя, а не для всего трафика — разворачивать anycast-сеть уровня Cloudflare/Google под 21,5% некэшируемого трафика экономически не оправдано.

### 3.6 Механизм регулировки трафика между ДЦ

- **Weighted geo-routing на GSLB** — веса ответа DNS равны текущей доле аудитории по регионам (§3.3), пересматриваются по факту роста DAU в каждом регионе.
- **Health-check + короткий TTL** — при отказе региона он исключается из ответа GSLB в течение TTL (десятки секунд), трафик перетекает на оставшийся регион.
- **Георезервирование объектного хранилища** между RU и KZ по умолчанию — при отказе одного региона данные остаются доступны из реплики другого без остановки сервиса.
- **Единый источник истины для Quota** в primary-регионе (RU) с асинхронной репликой в KZ и возможностью promote при аварии primary; для **Auth** реплицируется только общее состояние, а сама проверка идёт локально в каждом ДЦ. Quota не балансируется active-active между регионами (§3.1), в отличие от data-plane и edge-слоя.
